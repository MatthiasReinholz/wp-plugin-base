# Verified Manual Foundation Import

Use the manual importer when an existing application needs the complete, pinned
foundation tree without automatic synchronization, configuration edits, commits,
pushes, or change requests. Run it from an **already trusted** foundation checkout
or vendored installation. Do not download an unverified importer and execute it
to establish its own trust.

```bash
bash /path/to/trusted-foundation/scripts/update/import_foundation_release.sh \
  --version v1.9.0 \
  --expected-commit efa11cba9b980f400ddbbc3ca6115a3fb3aa2450 \
  --project-root /path/to/existing-plugin
```

The version and commit above identify the previously published release, not a
moving branch. For a later release, deliberately select its exact stable tag and
review its commit pin. `--expected-commit` is optional, but recommended when a
review or change proposal has already selected a commit. A mismatched pin stops
before source fetching or replacement.

Requirements: Python 3.10+, Bash, Git, curl, jq, and the supported cosign binary.
The existing GitHub release verifier requires `GH_TOKEN` or `GITHUB_TOKEN`, even
for a public repository. Supply the token through the process environment; never
put it in command arguments or remote URLs. A local-only managed profile removes
hosted automation requirements; it does not make online release verification an
offline operation. The GitLab verifier can use public anonymous access or its
existing `GITLAB_TOKEN`/`CI_JOB_TOKEN` support.

The default source is `MatthiasReinholz/wp-plugin-base` on GitHub. A deliberately
configured supported source can use `--source-provider github-release` or
`gitlab-release`, `--source-reference owner/repository`, `--source-api-base`, and
`--source-sigstore-issuer`. These are explicit foundation trust settings, separate
from the application's default branch and automation profile. Existing release
author and Sigstore policy settings remain effective; do not widen them to make
an untrusted release pass.

The importer:

1. Calls the current trusted `verify_foundation_release.sh` to enforce published,
   stable release metadata, allowed author, exact signed source/version/commit,
   protected release ancestry, and the configured exact Sigstore identity.
2. Fetches the verified commit and selected tag into an isolated bare Git
   repository with inherited Git configuration and tracing disabled. It checks
   the fetched tag still identifies the verified commit.
3. Materializes **every tracked regular file** directly from Git objects and
   verifies its blob identity, byte contents, membership, and executable flag.
   No imported code, checkout hooks, filters, or submodule commands are executed.
   Symlinks, submodules, unsafe paths, and case-colliding paths are rejected.
4. Repeats release verification before replacing `.wp-plugin-base`. It stages
   beside the destination, preserves the previous directory during replacement,
   and restores it if the ordinary replacement operation fails.

GitHub's autogenerated source ZIP/tar archives apply `export-ignore`, including
nested attributes. They are **not a complete foundation import**: the published
v1.9.0 tree has 460 tracked files, while its autogenerated archive omits 74,
including 14 child templates. A complete Git-object import deliberately ignores
that export policy. Do not replace this procedure with `git archive`.

The only permanent change is the target project's `.wp-plugin-base` directory.
Files use Git's supported modes: directories 0755, regular files 0644, executable
files 0755. Git does not record arbitrary directory permissions or special mode
bits. Existing destination contents and permissions are retained on ordinary
preparation or replacement failure. No `.git` metadata or authentication headers
are copied into the imported tree.

Before replacing a legacy vendor tree when a later sync will change automation
profiles, capture ownership using a reviewed new helper **while the old trusted
vendor is still installed**:

```bash
WP_PLUGIN_BASE_ROOT=/path/to/existing-plugin \
  bash /path/to/trusted-foundation/scripts/update/capture_automation_ownership.sh \
  /path/to/existing-plugin/.wp-plugin-base.env
```

This is an explicit separate operation: it records only automation files that
match the old vendored templates. It does not claim ownership of customized
application workflows. The importer itself never writes that receipt. Review
any mismatch before proceeding; preserve customized automation until ownership
is reconciled.

After importing, review the vendor diff and migration notes. Separately update
`FOUNDATION_VERSION` in application-owned configuration, decide which managed
profile and packs apply, then run sync and project validation. The importer does
not make these adoption decisions or change the application on your behalf.

## Concurrency and interrupted operations

Imports to one project cooperate through `.wp-plugin-base-import.lock`. A second
import fails without replacing files. This lock does not coordinate unrelated
editors, the automated updater, or arbitrary processes modifying the same files;
do not run those operations concurrently with a manual import.

Replacement uses two same-filesystem renames and ordinary-failure rollback. It
is not a crash-durable atomic directory exchange. `SIGKILL`, power loss, or a
failed rollback can leave an attempt directory named `.wp-plugin-base-import-*`
and the lock. Stop other import/update processes, inspect the lock's `owner` and
the attempt directory, and restore its `previous` directory if the destination
is absent. Keep any previous copy until the intended complete tree is confirmed.
Remove the stale lock only after verifying no importer is active, then retry.
The importer reports retained recovery paths when an ordinary rollback fails.

## Qualification

`python3 scripts/foundation/test_manual_foundation_import.py` exercises complete
tracked-tree materialization, export-ignored templates, executable permissions,
changing tags/releases, malformed receipts, pin mismatch, verification failures,
links, overlap, and staging/publication rollback. Transport and signature
fixtures test orchestration boundaries; real cryptographic release verification
remains covered by the existing signed-release acceptance checks.
